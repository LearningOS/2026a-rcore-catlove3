# 第三章 多道程序与分时多任务实验报告

## 功能总结

实现编号为 410 的 `sys_trace`，支持读取用户地址处的单字节、写入参数的低八位以及查询当前任务的系统调用次数。每个任务维护独立计数数组，在系统调用分发前递增，使查询包含本次调用。非法请求返回 `-1`，超出计数数组范围的编号查询返回 `0`。保留原有任务切换、时钟抢占和异常处理功能。

## 实现说明

`TaskControlBlock` 新增长度为 512 的 `syscall_times` 数组，初始值全部为零。任务管理器根据 `current_task` 访问对应任务的计数，因此一个任务的调用不会增加其他任务的计数。使用数组的 `get_mut` 和 `get` 处理编号边界，避免数组越界。

在 `syscall` 的入口统一递增计数，再分发到具体处理函数。`yield`、`exit` 等可能切换任务或不返回的调用，也在切换前完成统计。查询 `sys_trace` 本身的次数时，本次查询已经计入。

`sys_trace` 根据请求类型处理参数：

| 请求值 | 操作 | 返回值 |
| --- | --- | --- |
| 0 | 将 `id` 转为字节指针，读取一个无符号字节 | 读取值，范围为 0 到 255 |
| 1 | 将 `data` 转为 `u8`，写入 `id` 指向的地址 | 0 |
| 2 | 查询当前任务编号为 `id` 的系统调用次数 | 对应计数 |
| 其他值 | 不访问其他参数 | -1 |

本章尚未建立地址空间隔离，按题目约定直接访问传入地址，不检查地址是否合法。写入时 `as u8` 丢弃高位，符合只写入一个字节的要求。

## 简答题

### 用户态执行非法操作的结果

实验使用 QEMU 8.2.2 和课程仓库自带的 RustSBI 0.4.1 固件。

三个 `ch2b_bad_*.rs` 测例与其他任务一起运行，结果如下：

| 测例 | 执行的操作 | 实际行为 |
| --- | --- | --- |
| `ch2b_bad_address` | 向地址 `0x0` 写入一个字节 | 触发存储访问异常，内核打印 `PageFault in application`，其中 `bad addr = 0x0`，随后终止该任务 |
| `ch2b_bad_instructions` | 在 U 态执行 `sret` | 触发非法指令异常，内核打印 `IllegalInstruction in application`，随后终止该任务 |
| `ch2b_bad_register` | 在 U 态读取 `sstatus` | 触发非法指令异常，内核打印 `IllegalInstruction in application`，随后终止该任务 |

`PageFault` 是框架对存储访问故障和存储页故障共用的输出文字，并不表示本章已经启用分页。三个任务均未执行到失败提示，其他任务继续运行，说明用户程序不能通过上述指令获得 S 态权限，并且单个用户任务的异常不会终止所有任务。

### 进入 restore 时 sp 的含义和两种使用情景

刚进入 `__restore` 时，`sp` 指向待恢复任务的内核栈上的 `TrapContext` 起始地址。该结构保存 32 个通用寄存器槽位，以及 `sstatus`、`sepc`，共占用 `34 × 8 = 272` 字节。

第一种情景是任务首次启动：内核预先在该任务的内核栈上构造初始 `TrapContext`，令任务上下文的返回地址指向 `__restore`，通过 `__switch` 进入恢复过程。

第二种情景是从陷阱返回用户程序：`__alltraps` 保存现场并调用 `trap_handler`，处理完成后进入 `__restore`，恢复此前保存的现场。任务若曾在内核中被切换出去，会先恢复其内核执行过程，再完成陷阱返回。

### 特殊处理的寄存器及其意义

`ld t0, 32*8(sp)` 取出保存的 `sstatus`，再写回对应 CSR。其中 `SPP` 决定 `sret` 返回的特权级；返回 U 态时必须为 User。`SPIE` 等位用于恢复中断使能状态。

`ld t1, 33*8(sp)` 取出保存的 `sepc`，再写回对应 CSR。执行 `sret` 后，处理器从该地址继续取指。首次运行时是应用入口；系统调用返回时，内核已将保存的 `sepc` 增加 4，以跳过 `ecall`。

`ld t2, 2*8(sp)` 取出用户栈指针，暂存到 `sscratch`。此时恢复过程仍需使用内核栈，不能立即覆盖 `sp`；在恢复结束时通过交换指令将用户栈指针装入 `sp`。

### 为什么跳过 x2 和 x4

`x2` 是栈指针。若提前恢复它，后续加载寄存器时就会使用用户栈作为基址，无法继续读取内核栈上的 `TrapContext`。因此先把用户栈指针放到 `sscratch`，最后单独恢复。

`x4` 是线程指针 `tp`。本章应用未使用线程局部存储，框架约定不保存和恢复它。这是当前实现的简化；支持线程局部存储时需要相应处理。

### restore 末尾交换后两个寄存器的含义

在释放 `TrapContext` 的栈空间后，执行 `csrrw sp, sscratch, sp`：`sp` 变为恢复后的用户栈指针，`sscratch` 变为内核栈顶指针，为下次从用户态陷入内核做好准备。

### restore 中何时切换状态

特权级切换发生在 `sret`。该指令根据 `sstatus.SPP` 恢复特权级，并将程序计数器设置为 `sepc`。初始上下文将 `SPP` 设为 User；从 U 态陷入时，硬件也将之前的特权级记录为 User，因此恢复该状态后执行 `sret` 会进入 U 态。

### alltraps 开头交换后两个寄存器的含义

刚从 U 态陷入时，`sp` 仍保存用户栈指针，`sscratch` 保存内核栈顶。执行 `csrrw sp, sscratch, sp` 后，`sp` 指向内核栈顶，`sscratch` 保存陷入前的用户栈指针。随后在内核栈分配 `TrapContext` 并保存现场。

### 从 U 态进入 S 态发生在哪里

系统调用由用户程序的 `ecall` 触发。处理器根据异常委托配置进入 S 态，记录 `sepc`、`scause` 等状态，并跳转到 `stvec` 指定的 `__alltraps`。因此执行 `__alltraps` 第一条指令时已经处于 S 态，开头的栈交换不负责切换特权级。对于时钟中断和非法指令等陷阱，则是对应事件触发硬件切换，并不一定执行 `ecall`。

## 测试结果与运行方法

在 `ch3` 分支的仓库根目录执行 `make -C os run BASE=2 OFFLINE=1`，编译并运行 13 个官方用户程序，包含基础测例与作业测例。将 QEMU 实际输出交给官方检查脚本，结果如下：

| 检查脚本 | 结果 |
| --- | --- |
| `ci-user/check/ch3.py` | 7/7 |
| `ci-user/check/ch3b.py` | 4/4 |
| `ci-user/check/ch2b.py` | 5/5 |

这些分数表示各脚本的检查项数量，包含预期输出和禁止出现的输出，不是独立程序数量。`cargo fmt -- --check` 和 `git diff --check` 也通过。

`trace` 测例确认了读写字节、按任务统计、查询计入本次调用、未调用的系统调用计数为零等行为。休眠与主动让出 CPU 的测例正常通过。所有任务完成后，框架打印 `All applications completed!` 并关机；这条提示由框架原有的结束分支产生。关机使用课程框架提供的 SBI System Reset 接口，QEMU 正常退出。

在配置好课程要求的 Rust、cargo-binutils 和 QEMU 环境后，可在仓库根目录执行：

```bash
make -C os run BASE=2 OFFLINE=1
```

这条命令同时运行基础和作业测例。仅运行作业测例时使用 `BASE=0`。`OFFLINE=1` 跳过环境安装步骤，适用于依赖和工具已准备好的环境。

保留课程仓库原有的 RustSBI 固件、构建文件和评测配置，仅迁入系统调用实现与报告。将代码和 `reports/lab1.md` 一并推送到课程仓库的 `ch3` 分支，会触发课程评测。
